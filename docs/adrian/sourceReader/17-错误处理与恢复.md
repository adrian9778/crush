## 1. 架构概览

```

│ 错误处理层次                                                    │
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ 1. 哨兵错误 (Sentinel Errors)                           │  │
│  │    errors.Is / errors.As 匹配                           │  │

│  ├─────────────────────────────────────────────────────────┤  │

│  │    后端 → HTTP 状态码映射                                │  │

│  ├─────────────────────────────────────────────────────────┤  │
│  │ 4. 有界重试 (Bounded Retry)                             │  │
│  │    DB 事务冲突 3 次 / 服务器替换 3 次 / 锁轮询 100ms     │  │

│  ├─────────────────────────────────────────────────────────┤  │
│  │ 5. 认证重试 (Auth Retry)                                │  │
│  │    OAuth2 令牌刷新 / AWS SSO 浏览器认证                  │  │
│  │    交互式重认证等待 5 分钟                               │  │
│  │    RunComplete 合并防止误退出                            │  │
│  ├─────────────────────────────────────────────────────────┤  │
│  │ 6. 优雅关闭 (Graceful Shutdown)                         │  │
│  │    Agent 取消 → 消息刷新 → 并行清理 (5s 超时)            │  │
│  │    工作区引用计数 → 空闲延迟 → 服务器关闭                │  │
│  └─────────────────────────────────────────────────────────┘  │
```

每个哨兵错误对应特定的客户端行动：

| 哨兵错误 | 触发条件 | 客户端行动 |
|----------|----------|-----------|
| `ErrNotFound` | HTTP 404 | 重新注册工作区（服务器不再知道此 ID） |
| `ErrServerBusy` | HTTP 409（拒绝关闭） | 继续使用当前服务器 |
| `ErrServerShuttingDown` | HTTP 503 | 启动替换服务器并重试 |
| `ErrUnsupported` | HTTP 400 或 404 | 降级到旧服务器支持的行为 |

## 3. 错误传播与映射

### 后端错误到 HTTP 状态码

```
internal/server/proto.go
函数：handleError
偏移：+0 ～ +35
```

`handleError` 使用 `errors.Is` 将后端哨兵错误映射到 HTTP 状态码。映射规则见 [16-客户端服务器架构](16-客户端服务器架构.md) 第 3 节。

关键设计决策：

- `ErrClientNotAttached` → 409 而非 404：工作区存在但无活动流，404 会误导客户端执行工作区恢复
- `ErrServerShuttingDown` → 503 而非 409：请求没错，进程正在离开，客户端应重试到替换服务器

### HTTP 状态码到客户端哨兵错误

```
internal/client/errors.go
函数：checkStatus
偏移：+0 ～ +22
```

`checkStatus` 将 HTTP 响应状态码转换为错误，使用**双重包装**模式：

```go
case http.StatusNotFound:
    return fmt.Errorf("%w: %w", ErrNotFound, err)
case http.StatusServiceUnavailable:
    return fmt.Errorf("%w: %w", ErrServerShuttingDown, err)
```

双重包装使调用者可以同时 `errors.Is(err, ErrNotFound)` 判断语义和获取详细消息。

其他状态码（非 200、非 404、非 503）返回普通错误（不带哨兵），表示不可行动的传输失败。

### Agent 运行错误传播

```
internal/backend/agent.go
函数：runAgent
偏移：+0 ～ +35
```

Agent 运行错误的传播路径：

1. `RunAccepted` 返回错误
2. `context.Canceled` → 直接返回（sessionAgent.Run 已发布取消标记）
3. 其他错误 → `AgentNotifications().Publish` 发送 `TypeAgentError` 通知（lossy）
4. 如果有 RunID 且 coordinator 未发布终端事件 → `RunCompletions().PublishMustDeliver` 发送错误终端事件（reliable）

### 非交互模式错误处理

```
internal/app/app.go
函数：RunNonInteractive
偏移：+145 ～ +155
```

```go
if errors.Is(result.err, context.Canceled) || errors.Is(result.err, agent.ErrRequestCancelled) {
```

## 4. Panic 恢复

### 通用 Panic 恢复工具

```
internal/log/log.go
函数：RecoverPanic
偏移：+0 ～ +22
```

`RecoverPanic` 是通用 panic 恢复工具：

1. `recover()` 捕获 panic
2. `event.Error(r, "panic", true, "name", name)` — 发送错误事件
3. 创建带时间戳的 panic 日志文件：`crush-panic-<name>-<timestamp>.log`
4. 写入 panic 信息、时间、堆栈跟踪
5. 执行可选的 cleanup 函数

使用位置：`app.Subscribe` 在 TUI 事件处理 goroutine 中调用 `log.RecoverPanic`。

### HTTP 中间件 Panic 恢复

```
internal/server/recover.go

偏移：+0 ～ +22
```

HTTP 中间件层的 panic 恢复：

1. 包装 `ResponseWriter` 为 `recoverResponseWriter`（跟踪 `wroteHeader`）
2. `defer recover()` 捕获 panic
3. `http.ErrAbortHandler` 重新 panic（保留标准库约定）
4. 其他 panic：记录日志 + 堆栈
5. 如果响应未开始：写入 500 JSON 错误
6. 如果响应已开始：连接被静默关闭

## 5. 有界重试策略

### 数据库事务冲突重试

```
internal/history/file.go
函数：createWithVersion
偏移：+0 ～ +50
```

文件创建时的 UNIQUE 约束冲突重试：

```
const maxRetries = 3
```

重试逻辑：

1. 开始事务
2. 尝试 `CreateFile`（指定版本号）
3. UNIQUE 约束冲突 → 回滚 + 版本号递增 + 重试
4. 其他错误 → 回滚 + 返回错误
5. 成功 → 提交 + 发布事件
6. 超过 `maxRetries` → 返回冲突错误

### 服务器替换重试

```
internal/cmd/root.go
函数：createWorkspaceOnLiveServer
偏移：+0 ～ +18
```

```
const maxStaleServerRetries = 3
```

工作区创建时服务器正在关闭的重试：

1. 尝试 `CreateWorkspace`
2. `ErrServerShuttingDown` → 调用 `replaceExitingServer` 启动新服务器
3. 重试创建
4. 超过 `maxStaleServerRetries` → 返回错误

`replaceExitingServer` 等待旧套接字消失后启动新服务器——此竞态不可避免：服务器在无客户端时决定退出，新客户端在退出决定和套接字消失之间到达。

### 文件锁轮询重试

```
internal/lock/lock_unix.go
函数：lockFile
偏移：+0 ～ +15
```

```
const retrySleep = 100 * time.Millisecond
```

非阻塞 `flock` + `LOCK_NB` 的轮询重试：

1. `unix.Flock(fd, LOCK_EX|LOCK_NB)`
2. `EWOULDBLOCK` → `time.After(retrySleep)` 等待
3. `ctx.Done()` → 返回 context 错误
4. 成功 → 返回解锁函数

Windows 平台使用 `LockFileEx` + `LOCKFILE_FAIL_IMMEDIATELY`，同样的 100ms 轮询模式。

### 模型降级 Fallback

```

函数：title generation
偏移：+0 ～ +20
```

标题生成时的模型降级重试：

```go

```

先尝试小模型（快、便宜），失败或超 token 限制时降级到大模型（更强大）。这是降级而非重试——后续尝试使用不同的模型。

Hook 命令执行的超时放弃机制——`runOne` 在 context 取消后等待 1 秒让 Shell goroutine 自行退出，然后返回控制权。镜像 `cmd.WaitDelay = time.Second` 的行为。

### 401 检测


```go

    var providerErr *fantasy.ProviderError
    return errors.As(err, &providerErr) && providerErr.StatusCode == http.StatusUnauthorized

```

使用 `errors.As` 检查 LLM 提供商返回的 401 错误。

### 认证刷新回调

```
函数：retryAfterUnauthorized
偏移：+0 ～ +27
```

根据提供商配置类型选择刷新策略：

| 提供商类型 | 刷新方式 | 失败处理 |
|-----------|---------|---------|
| OAuth2 (`OAuthToken != nil`) | `refreshOAuth2Token` | 令牌被吊销 → 交互式重认证 |
| AWS SSO (`AWSAuthRefresh != ""`) | `refreshAWSCredentials` | 返回错误 |
| API Key 模板 (`APIKeyTemplate` 含 `$`) | `refreshApiKeyTemplate` | 返回错误 |
| 其他 | 返回 nil（不刷新，直接重试） | — |

返回 nil 表示"请重试请求"，返回错误表示"刷新失败，不重试"。

### 交互式重认证

```
函数：waitForInteractiveReauth
偏移：+0 ～ +25
```

OAuth2 令牌被吊销时的交互式重认证流程：

1. 创建**分离 context**（`context.WithoutCancel(ctx)`）+ 5 分钟超时——等待在 agent 运行取消后仍然存活，给用户足够时间完成浏览器认证
2. `c.cfg.WaitForTokenChange(waitCtx, providerID)` — 阻塞等待令牌变更
3. 如果原始 context 在等待期间被取消：返回 `ctx.Err()`（不能重试）
4. `c.UpdateModels(waitCtx)` — 重建模型使新凭证生效
5. 返回 nil（信号"请重试"）

### AWS SSO 刷新

```

```

AWS SSO 凭证刷新通过 `aws sso login` 命令执行，5 分钟超时，验证 URL 通过通知系统推送到 UI。

### RunComplete 合并

```
internal/agent/coordinator.go
偏移：+10 ～ +30 (在 Run 方法附近)
```

认证重试时的 RunComplete 合并机制：

```go
var (
    latest    notify.RunComplete
    hasLatest bool
)
onComplete := func(rc notify.RunComplete) {
    latest = rc
    hasLatest = true
}
```

第一次尝试的失败 `RunComplete`（unauthorized）会被第二次尝试的结果覆盖。最终通过 `PublishMustDeliver` 发布唯一终端事件。防止 `crush run` 在重试成功前因旧错误退出。

### 认证重试循环

实际的认证重试循环由 `fantasy`（Agent 框架）内置处理。`makeAuthRefreshCallback` 将 `retryAfterUnauthorized` 连接到 fantasy 的 `OnAuthRefresh` 回调。fantasy 在收到 401 后调用回调，如果返回 nil 则自动重试。

## 7. 优雅关闭

### 服务器优雅关闭

```
internal/cmd/server.go
函数：serverCmd.RunE
偏移：+30 ～ +70
```

服务器进程的信号处理和优雅关闭：

1. `signal.Notify(sigch, os.Interrupt + SIGTERM)` — 注册信号
2. goroutine 中 `srv.ListenAndServe()`
3. `select`：
   - 信号到达 → 进入关闭流程
   - `errch` 收到错误 → 检查是否为 `ErrServerClosed`
4. `ErrServerClosed` → 直接返回 nil（后端触发的空闲关闭）
5. 其他情况：`context.WithTimeout(5s)` + `srv.Shutdown(ctx)`

### App 优雅关闭

```
internal/app/app.go
函数：Shutdown
偏移：+0 ～ +55
```

应用层有序关闭：

1. **取消所有 Agent**：`AgentCoordinator.CancelAll()` — 等待 Agent 完成，确保它们能写入最终状态
2. **创建 5 秒关闭 context**：`context.WithTimeout(context.Background(), 5*time.Second)`
3. **刷新消息**：`Messages.FlushAll(shutdownCtx)` — 确保缓冲的流式增量写入 DB
4. **并行清理**（`sync.WaitGroup`）：
   - 发送 `event.AppExited()` 事件
   - `shell.GetBackgroundShellManager().KillAll(shutdownCtx)` — 杀死后台 Shell
   - `app.herdrClient.Close()` — 关闭 herdr 客户端
   - `app.LSPManager.KillAll(shutdownCtx)` — 关闭所有 LSP 客户端
   - 逐个执行 `app.cleanupFuncs`（DB 释放、MCP 关闭、事件 broker 清理）
5. **`wg.Wait()`** — 等待所有清理完成

### Backend 空闲关闭

```
internal/backend/backend.go
函数：scheduleShutdownIfIdleLocked
偏移：+0 ～ +15
```

后端空闲关闭决策（在 `b.mu` 下调用）：

1. 无 `shutdownFn` → 不关闭
2. 有工作区或有 pending 创建 → 不关闭
3. `lingerDelay <= 0` → 立即关闭（锁存 `closing`）
4. `lingerDelay > 0` → 启动延迟定时器（默认 60 秒）

延迟定时器在 `maybeShutdown` 中重新检查空闲状态——如果在新工作区到达期间定时器被取消，不会误关闭。

### Workspace 关闭顺序

```
函数：Workspace.Shutdown
偏移：+0 ～ +15
```

工作区关闭的安全顺序：

1. `closing = true` — 阻止新 agent 运行
2. `w.cancel()` — 取消工作区 context
3. `w.AgentCoordinator.CancelAll()` — 取消已注册的 per-session cancel
4. `w.runWG.Wait()` — 等待已派发的 agent goroutine 返回
5. `w.App.Shutdown()` — DB、LSP 等资源清理

关键保证：cancel → CancelAll → runWG.Wait 在 DB 清理之前完成。

## 8. 工作区恢复

### SSE 重连循环

```
internal/workspace/client_workspace.go
函数：runSubscription
偏移：+0 ～ +70
```

客户端工作区的 SSE 事件流重连机制：

1. **指数退避**：初始 250ms，最大 10s
2. **降级状态管理**：仅在状态变化时通知 UI，避免重复通知
3. **404 处理**：`ErrNotFound` 触发 `recoverWorkspace` 重新注册
4. **其他错误**：降级 + 退避重试
5. **流关闭**：`ErrStreamClosed` + 退避重连
6. **升级机制**：连续 20 次恢复失败后标记 `Stuck`（UI 升级为持久错误），但循环不停止

1. 创建独立 context（`WithoutCancel(subCtx)`）——服务器不在请求连接断开时放弃创建
2. 30 秒超时
3. `client.CreateWorkspace` 从缓存快照重建
4. 更新缓存的 `proto.Workspace`（新 ID）
5. 重新初始化 agent

## 10. MCP 生命周期恢复

### 配置对账

```
internal/agent/tools/mcp/lifecycle.go
函数：reconcile
偏移：+0 ～ +40
```

MCP 配置变更时的对账逻辑——纯函数，计算需要采取的行动：

1. 遍历配置中的所有 MCP 服务器
2. 对比当前状态和期望状态
3. 失败/错误/需要认证的服务器 → 标记重启（每次配置写入时重试）
4. 配置变更的运行中服务器 → 标记重启
5. 配置中移除的服务器 → 标记拆卸
6. 新增服务器 → 标记初始化

### Panic 安全的初始化

```
internal/agent/tools/mcp/init.go
函数：goInitClient
偏移：+0 ～ +30
```

MCP 客户端初始化在 goroutine 中执行，带 panic 恢复。panic 被转换为错误并更新状态为 `StateError`。

### Generation 号防护

```
internal/agent/tools/mcp/init.go
```

`currentGen` 单调递增的 generation 号确保并发 teardown 使过期的异步初始化结果无效。初始化完成时检查 generation 号是否仍匹配，不匹配则丢弃结果。

### 冷却重试

```
internal/lsp/manager.go
```

LSP 服务器启动失败后的 30 秒冷却期——在冷却期内不重试同一服务器的启动，避免快速循环消耗资源。MCP 服务器使用类似的状态机，错误状态下需要配置变更触发恢复。
