## 1. 构建系统总览

Crush 的构建与部署体系由三层组成：本地开发用 Taskfile、持续集成用 GitHub Actions、正式发布用 GoReleaser Pro。三者共享同一套核心编译参数（`CGO_ENABLED=0`、`GOEXPERIMENT=greenteagc`）和版本注入机制（ldflags → `internal/version` 包）。

```
┌──────────────────────────────────────────────────────────────────┐
│                        构建与部署全景                             │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  开发者本地            GitHub CI                  发布            │
│  ┌──────────┐     ┌──────────────┐     ┌──────────────────┐     │
│  │ Taskfile │     │ build.yml    │     │ release.yml      │     │
│  │ build    │────▶│ lint.yml     │────▶│ (tag push)       │     │
│  │ run      │     │ security.yml │     │   ↓              │     │
│  │ test     │     │ snapshot.yml │     │ GoReleaser Pro   │     │
│  │ lint     │     │ nightly.yml  │     │   ↓              │     │
│  └──────────┘     └──────────────┘     │ 7 OS × 4 Arch    │     │
│                                        │ Cosign + SBOM    │     │
│                                        │ AUR/Homebrew/... │     │
│                                        └──────────────────┘     │
│                                                                  │
│  版本注入: -ldflags="-X version.Version=..."                     │
│  编译环境: CGO_ENABLED=0, GOEXPERIMENT=greenteagc               │
│  Go 版本:  1.26.6                                               │
└──────────────────────────────────────────────────────────────────┘
```

**关键文件清单**：

| 文件 | 角色 |
|------|------|
| `Taskfile.yaml` | 本地构建运行器，定义 build/run/test/lint/release 等任务 |

| `main.go` | 程序入口点，36 行 |

## 2. Taskfile 构建运行器

### 2.1 全局环境

源码位置：`Taskfile.yaml` → `vars:` / `env:` 段

```yaml
vars:
  VERSION:
    sh: git describe --long 2>/dev/null || echo ""
  RACE:
    sh: test -f race.log && echo "1" || echo ""

env:
  CGO_ENABLED: 0
  GOEXPERIMENT: greenteagc
```

两个全局环境变量贯穿所有构建任务：`CGO_ENABLED=0` 禁用 cgo 以实现纯静态交叉编译；`GOEXPERIMENT=greenteagc` 启用实验性 GC 优化。`VERSION` 变量通过 `git describe --long` 动态获取，为空时 ldflags 不注入版本号。`RACE` 变量检测 `race.log` 文件是否存在，存在时构建附加 `-race` 标志。

### 2.2 build 任务

源码位置：`Taskfile.yaml` → `tasks.build`

```yaml
build:
  desc: Run build
  vars:
    LDFLAGS: '{{if .VERSION}}-ldflags="-X .../version.Version={{.VERSION}}"{{end}}'
  cmds:
    - "go build -v {{if .RACE}}-race{{end}} {{.LDFLAGS}} ."
  sources:
    - ./**/*.go
    - go.mod
    - internal/agent/**/*.md
    - internal/agent/**/*.md.tpl
    - internal/agent/hyper/provider.json
  generates:
    - crush{{exeExt}}
```

`sources` 列表不仅包含 `.go` 文件，还包含 Agent 提示词模板（`*.md`、`*.md.tpl`）和 Hyper provider 配置（`provider.json`），因为这些文件通过 `go:embed` 编入二进制。Taskfile 的增量构建检测会在这些源文件未变更时跳过重新编译。

`LDFLAGS` 仅在 `VERSION` 非空时生成，将 git tag 传递给 `internal/version.Version` 变量。

### 2.3 install 任务

源码位置：`Taskfile.yaml` → `tasks.install`

install 任务与 build 类似，但使用 `go install` 将二进制安装到 `$GOPATH/bin`。它先执行 `fetch-tags` 子任务（删除本地 `nightly` tag 并从远程拉取最新 tags），再执行 `go install` 并注入相同的 ldflags。

### 2.4 test 任务

源码位置：`Taskfile.yaml` → `tasks.test`

```yaml
test:
  desc: Run tests
  cmds:
    - go test -race -failfast ./... {{.CLI_ARGS}}
```

测试始终附加 `-race`（竞态检测器）和 `-failfast`（首个失败即停止）。`test:record` 任务用于重新录制 VCR 测试磁带——删除 `internal/agent/testdata` 目录后以 `-v -count=1 -timeout=1h` 运行 Agent 包测试。

### 2.5 release 任务

源码位置：`Taskfile.yaml` → `tasks.release`

```yaml
release:
  desc: Create and push a new tag following semver
  vars:
    NEXT:
      sh: svu next --always || go run github.com/caarlos0/svu/v3@latest next --always
  prompt: "This will release {{.NEXT}}. Continue?"
  preconditions:
    - sh: '[ $(git symbolic-ref --short HEAD) = "main" ]'
      msg: Not on main branch
    - sh: "[ $(git status --porcelain=2 | wc -l) = 0 ]"
      msg: "Git is dirty"
    - sh: 'gh run list --workflow build.yml --commit $(git rev-parse HEAD) --status success ...'
      msg: "Test build for this commit failed or not present"
    - sh: 'gh run list --workflow snapshot.yml --commit $(git rev-parse HEAD) --status success ...'
      msg: "Snapshot build for this commit failed or not present"
  cmds:
    - task: fetch-tags
    - git commit --allow-empty -m "{{.NEXT}}"
    - git tag --annotate --sign -m "{{.NEXT}}" {{.NEXT}} {{.CLI_ARGS}}
    - echo "Pushing {{.NEXT}}..."
    - git push origin main --follow-tags
```

release 任务有四个前置条件（`preconditions`），全部通过才会执行：

1. **必须位于 main 分支** — `git symbolic-ref --short HEAD` 必须输出 `main`
2. **Git 工作区必须干净** — `git status --porcelain=2` 必须无输出
3. **当前提交的 build CI 必须成功** — 通过 `gh run list` 查询 build.yml 工作流状态
4. **当前提交的 snapshot CI 必须成功** — 同上查询 snapshot.yml

版本号通过 `svu next --always` 自动推导（语义化版本），用户确认后创建空提交、签名标注 tag（`--annotate --sign`），然后推送 main 分支和 tags。tag 推送触发 release.yml 工作流。

### 2.6 辅助任务

| 任务 | 用途 |
|------|------|
| `lint` | 运行 golangci-lint + 日志大写检查脚本 |
| `lint:fix` | golangci-lint 自动修复 |

## 3. Go 模块与依赖

### 3.1 模块定义

源码位置：`go.mod` → 前 50 行

模块路径 `github.com/charmbracelet/crush`，Go 版本 `1.26.6`。项目有 40+ 个直接依赖，主要包括：

- **Charm 生态**：`charm.land/bubbletea/v2`（TUI 框架）、`charm.land/lipgloss/v2`（样式）、`charm.land/fang/v2`（CLI 框架）、`charm.land/log/v2`（日志）、`github.com/charmbracelet/x/ansi`、`github.com/charmbracelet/x/term`
- **CLI**：`github.com/spf13/cobra`（命令行框架）
- **数据库**：`github.com/jmoiron/sqlx` + `modernc.org/sqlite`（纯 Go SQLite 驱动，无 cgo）
- **传输**：`github.com/charmbracelet/crush/internal/server` 使用标准库 `net/http` + `golang.org/x/net/http2/h2c`
- **MCP**：`github.com/modelcontextprotocol/go-sdk` 
- **LLM Provider SDK**：`github.com/anthropics/anthropic-sdk-go`、`github.com/mark3labs/mcp-go`、`github.com/openai/openai-go`
- **配置**：`github.com/spf13/viper`（配置管理）
- **日志轮转**：`gopkg.in/natefinch/lumberjack.v2`
- **其他**：`github.com/google/uuid`、`github.com/muesli/termenv`、`github.com/charmbracelet/x/exp`

### 3.2 无 Vendoring

项目不使用 `vendor/` 目录，依赖从 Go 模块代理拉取。GoReleaser 构建前执行 `go mod tidy` 确保依赖一致性。

### 3.3 无 Dockerfile

项目不包含 Dockerfile。GoReleaser 的 `nfpm` 配置可以生成容器镜像格式（apk/deb/rpm），但 Crush 本身不容器化运行——它是终端应用程序，直接在宿主机执行。

## 4. 入口点与命令行结构

### 4.1 main.go

源码位置：`main.go`（全量 36 行）

```go
func main() {
    if os.Getenv("CRUSH_PROFILE") == "true" {
        go func() {
            _ = http.ListenAndServe("localhost:6060", nil)
        }()
    }
    cmd.Execute()
}
```

入口点极简：当环境变量 `CRUSH_PROFILE=true` 时在后台启动 pprof HTTP 服务器（`:6060`），然后调用 `cmd.Execute()`。`cmd.Execute()` 定义在 `internal/cmd/root.go` 中，初始化 cobra 根命令并执行。

源码位置：`internal/cmd/root.go` → `init()` 函数（偏移 ~57-80）

```
├── projects (projectsCmd)
```

根命令的 `RunE` 函数（偏移 ~112-153）执行交互式 TUI 模式：创建工作区、初始化 Bubble Tea 程序、运行 TUI 循环。`run` 子命令执行非交互式单次提示。`server` 子命令独立启动后端 HTTP 服务器。

### 4.4 server 子命令

源码位置：`internal/cmd/server.go`（全量 100 行）

server 子命令独立启动后端服务器，不启动 TUI。其流程：

```
serverCmd.RunE
  ├── config.Load()            — 加载配置
  ├── server.ParseHostURL()    — 解析主机 URL
  ├── crushlog.Setup()         — 日志设置
  ├── server.NewServer()       — 创建服务器实例
  ├── go srv.ListenAndServe()  — 后台启动监听
  ├── 等待信号或错误
  │   ├── sigch (SIGINT)       — 收到中断信号
  │   └── errch                — 服务器错误
  └── srv.Shutdown(ctx, 5s)    — 5 秒超时优雅关闭
```

信号处理通过 `addSignals` 函数追加平台特定信号（在 `server_windows.go` 中定义 Windows 信号）。

### 4.5 run 子命令

源码位置：`internal/cmd/run.go`（全量 731 行）

run 子命令支持两种模式：客户端-服务器模式（`useClientServer()` 返回 true 时）和本地模式。客户端-服务器模式下通过 `connectToServer` 连接到已有服务器，创建 `ClientWorkspace` 并执行 `runNonInteractive`。本地模式下创建 `AppWorkspace` 并调用 `App.RunNonInteractive`。

`runNonInteractive` 函数（偏移 ~173-317）处理 SSE 事件流，通过 `runStream.handle` 方法将事件转换为 stdout 输出。RunID 机制确保在繁忙会话中正确关联终端 RunComplete 事件。

## 5. 版本注入系统

### 5.1 版本变量

源码位置：`internal/version/version.go` → 包变量声明（偏移 ~11-19）

```go
var (
    Version = "devel"
    Commit  = "unknown"
    BuildID = ""
)
```

三个变量在编译时通过 ldflags 注入。未注入时使用默认值：`Version="devel"`、`Commit="unknown"`、`BuildID=""`。

### 5.2 ldflags 注入点

版本注入在三个地方发生：

**1. Taskfile build/install**（`Taskfile.yaml` → `tasks.build.vars.LDFLAGS`）：
```
-ldflags="-X github.com/charmbracelet/crush/internal/version.Version={{.VERSION}}"
```
仅注入 `Version`，`VERSION` 来自 `git describe --long`。

**2. GoReleaser**（`.goreleaser.yml` → `builds[0].ldflags`）：
```
-s -w -X github.com/charmbracelet/crush/internal/version.Version={{.Version}}
```
同时注入 `-s -w`（去除符号表和 DWARF 调试信息以减小二进制大小）。

**3. AUR 构建**（`.goreleaser.yml` → `aur_sources[0].build`）：
```
-ldflags="-w -s -buildid='' -linkmode=external -X .../version.Version=v${pkgver}"
```
AUR 包从预编译二进制安装，但仍运行 `go build` 以保持一致性。

### 5.3 init() 回退

源码位置：`internal/version/version.go` → `init()` 函数（偏移 ~25-38）

当用户通过 `go install github.com/charmbracelet/crush@latest` 安装时（无 ldflags），`init()` 函数从 `debug.ReadBuildInfo()` 读取模块版本作为回退：

```go
func init() {
    info, ok := debug.ReadBuildInfo()
    if ok {
        mainVersion := info.Main.Version
        if mainVersion != "" && mainVersion != "(devel)" {
            Version = mainVersion
        }
    }
    if BuildID == "" {
        BuildID = deriveBuildID()
    }
}
```

`debug.ReadBuildInfo()` 仅在 `go install` 构建时返回有意义的主模块版本（非 `(devel)`），`go build` 不设置此值。

### 5.4 deriveBuildID

源码位置：`internal/version/version.go` → `deriveBuildID()` 函数（偏移 ~43-53）

```go
func deriveBuildID() string {
    exe, err := os.Executable()
    if err != nil {
        return "unknown"
    }
    fi, err := os.Stat(exe)
    if err != nil {
        return "unknown"
    }
    return strconv.FormatInt(fi.ModTime().UnixNano(), 36)
}
```

`BuildID` 在未通过 ldflags 注入时，从可执行文件的修改时间派生（Unix 纳秒时间戳的 36 进制表示）。这确保每次重新编译产生不同的 `BuildID`，用于开发期间检测陈旧服务器——见文档 16 中的客户端重连和工作区恢复逻辑。

### 5.5 版本信息流

```
┌───────────────────┐    ldflags     ┌──────────────────┐
│ git describe/tag  │──────────────▶│ version.Version  │
└───────────────────┘                │ version.Commit   │
                                     │ version.BuildID  │
┌───────────────────┐    init()      │                  │
│ debug.ReadBuildInfo│───回退──────▶│  (仅 go install) │
└───────────────────┘                └────────┬─────────┘
                                              │
┌───────────────────┐    ModTime     ┌────────▼─────────┐
│ os.Executable()   │──────────────▶│ version.BuildID  │
│ os.Stat().ModTime │   (36进制)    │  (开发构建回退)   │
└───────────────────┘                └──────────────────┘
```

## 6. GoReleaser 发布管道

### 6.1 配置总览

源码位置：`.goreleaser.yml`（全量 351 行）

GoReleaser Pro v2 配置。关键字段：

```yaml
version: 2
project_name: crush
includes:
  - from_url:
      url: charmbracelet/meta/main/notarize.yaml
```

通过 `from_url` 包含 Charm 组织共享的 macOS 公证配置（`notarize.yaml`），避免在每个项目重复公证逻辑。

### 6.2 构建矩阵

源码位置：`.goreleaser.yml` → `builds[0]`

```yaml
builds:
  - env:
      - CGO_ENABLED=0
      - GOEXPERIMENT=greenteagc
    goos: [linux, darwin, windows, freebsd, openbsd, netbsd, android]
    goarch: [amd64, arm64, "386", arm]
    goarm: ["7"]
    ignore:
      - goos: android, goarch: amd64
      - goos: android, goarch: arm
      - goos: android, goarch: "386"
      - goos: windows, goarch: arm
    ldflags:
      - -s -w -X .../version.Version={{.Version}}
    flags:
      - -trimpath
```

7 个操作系统 × 4 个架构 = 28 种组合，减去 4 个忽略项 = **24 个目标构建**。`goarm=7` 指定 ARMv7 为唯一 ARM 架构变体。`-trimpath` 从二进制中移除本地文件路径（可重现构建 + 安全）。

### 6.3 预构建钩子

源码位置：`.goreleaser.yml` → `before.hooks`

```yaml
before:
  hooks:
    - go mod tidy
    - rm -rf completions && mkdir completions
    - rm -rf manpages && mkdir manpages
    - sh -c 'go run . completion bash >./completions/crush.bash'
    - sh -c 'go run . completion zsh >./completions/crush.zsh'
    - sh -c 'go run . completion fish >./completions/crush.fish'
    - sh -c 'go run . man | gzip -c >./manpages/crush.1.gz'
```

构建前生成三种 shell 自动补全（bash/zsh/fish）和压缩的手册页（`crush.1.gz`），这些文件随后被打包进各平台的分发包中。

### 6.4 归档

源码位置：`.goreleaser.yml` → `archives[0]`

归档名称模板将架构名映射为友好名称：`amd64` → `x86_64`，`386` → `i386`。每个归档包含 README、LICENSE、手册页和补全文件。Windows 使用 zip 格式，其他平台使用 tar.gz。

### 6.5 签名与 SBOM

源码位置：`.goreleaser.yml` → `signs` / `sboms`

```yaml
signs:
  - cmd: cosign
    signature: "${artifact}.sigstore.json"
    args: [sign-blob, --bundle=${signature}, ${artifact}, --yes]
    artifacts: checksum
    output: true

sboms:
  - artifacts: archive
  - id: source
    artifacts: source
```

使用 **Cosign** 对 `checksums.txt` 进行 sigstore 签名（密钥less签名）。SBOM（软件物料清单）为归档和源码各生成一份。

### 6.6 快照与每日构建

源码位置：`.goreleaser.yml` → `snapshot` / `nightly`

```yaml
nightly:
  publish_release: true
  keep_single_release: true
  version_template: "{{ incminor .Version }}-nightly"

snapshot:
  version_template: "0.0.0-{{ .Timestamp }}"
```

快照版本使用 `0.0.0-<时间戳>` 格式，每日构建使用 `<次版本号>-nightly` 格式。每日构建只保留最新一个发布（`keep_single_release: true`）。

### 6.7 变更日志

源码位置：`.goreleaser.yml` → `changelog`

### 7.1 平台特定文件

**Windows**（`_windows.go`）：

- `internal/server/net_windows.go` — Windows 传输（npipe/TCP）
- `internal/shell/exec_windows.go` — Windows Shell 执行

**Darwin**（`_darwin.go`）：
- `internal/ui/notification/icon_darwin.go` — macOS 通知图标

### 7.2 GoReleaser 忽略矩阵

源码位置：`.goreleaser.yml` → `builds[0].ignore`

忽略的目标组合：
- android + amd64 — Android 仅支持 arm64
- android + arm — 已由 goarm=7 覆盖但 Android NDK 不支持此变体
- android + 386 — Android不支持 32 位 x86
- windows + arm — Windows ARM 32 位不被官方支持

最终构建 24 个二进制：linux(4)、darwin(2)、windows(3)、freebsd(4)、openbsd(4)、netbsd(4)、android(1) — 实际数量取决于具体架构组合。

### 7.3 传输层平台差异

| 平台 | 传输方式 | 源码位置 |
|------|---------|---------|
| Unix | Unix 域套接字 | `internal/server/net_other.go` → `listen()` |
| Windows | 命名管道 (npipe) 或 TCP | `internal/server/net_windows.go` → `listen()` |

Unix 域套接字路径通过 `socketDir()` 计算：优先 `$XDG_RUNTIME_DIR`，回退 `os.TempDir()`，套接字名 `crush-<uid>.sock`，最大路径 104 字符。Windows 使用 `\\.\pipe\crush-<pid>` 命名管道，或通过 `--host` 指定 TCP 地址。

详见文档 16 第 2 节"传输层"。

源码位置：`.github/workflows/snapshot.yml`（全量 35 行）

```yaml

  push:
    branches: [main]

  snapshot:
    runs-on:
      group: releasers
    steps:

      - uses: actions/setup-go@v7.0.0
```

### 8.5 nightly.yml — 每日构建

源码位置：`.github/workflows/nightly.yml`（全量 31 行）

```yaml
on:
  schedule:
    - cron: "0 0 * * *"  # every day at midnight
  workflow_dispatch:

jobs:
  check:
    outputs:
      should_run: ${{ steps.check.outputs.should_run }}
    steps:
      - id: check
        run: |
          if gh run list --workflow nightly.yml -c $(git rev-parse HEAD) -s success | grep 'completed'; then
            echo "should_run=false" >> $GITHUB_OUTPUT
          else
            echo "should_run=true" >> $GITHUB_OUTPUT
          fi
  nightly:
    needs: check
    if: needs.check.outputs.should_run == 'true'
    uses: charmbracelet/meta/.github/workflows/nightly.yml@main
    secrets:
      goreleaser_key: ${{ secrets.GORELEASER_KEY }}
```

每天午夜（UTC）触发。先通过 `check` 作业检查当前 HEAD 是否已成功运行过 nightly——如果是则跳过（避免重复构建）。`workflow_dispatch` 允许手动触发。nightly 作业同样复用 meta 仓库的可复用工作流。

### 8.7 security.yml — 安全扫描

源码位置：`.github/workflows/security.yml`（全量 93 行）

四个安全作业：

**1. CodeQL** — GitHub 语义代码分析，扫描 Go 和 GitHub Actions 语言的漏洞。在 PR、push 到 main、每日定时触发。

**2. Grype** — Anchore Grype 漏洞扫描器，扫描整个仓库。`severity-cutoff: critical` 仅在发现严重漏洞时失败。结果上传为 SARIF。

**4. dependency-review** — 仅在 PR 时运行，检查新增依赖的许可证和漏洞。`fail-on-severity: critical`，允许的许可证白名单：BSD-2/3-Clause、MIT、MIT-0、Apache-2.0、MPL-2.0、ISC、Unlicense 及 Go 专利许可证。

```yaml
      include: "scope"
    groups:
      all:
        patterns: ["*"]
    ignore:
      - dependency-name: github.com/charmbracelet/bubbletea/v2
        versions: [v2.0.0-beta1]
      - dependency-name: github.com/charmbracelet/lipgloss/v2
        versions: [v2.0.0-beta1]
      - dependency-name: mvdan.cc/sh/moreinterp

  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"
    labels: ["area: dependencies"]
    commit-message:
      prefix: "chore"
      include: "scope"
    groups:
      all:
        patterns: ["*"]
```

两个生态系统：

**Go 模块**（`gomod`）— 每月检查一次依赖更新。所有依赖分一组批量更新（`groups.all.patterns: ["*"]`）。提交消息前缀 `chore(deps):`。三个忽略规则：
- `bubbletea/v2` 的 `v2.0.0-beta1` — 跳过 beta 版本
- `lipgloss/v2` 的 `v2.0.0-beta1` — 同上
- `mvdan.cc/sh/moreinterp` — 完全忽略所有更新

**GitHub Actions**（`github-actions`）— 每月检查 Action 版本更新，同样批量分组更新。

### 12.2 手动依赖更新

源码位置：`Taskfile.yaml` → `tasks.deps`

```yaml
deps:
  desc: Update Fantasy and Catwalk
  env:
    GOPROXY: direct
    GONOSUMDB: charm.land/*
  cmds:
    - go get charm.land/fantasy@latest
    - go get charm.land/catwalk@latest
    - go mod tidy
```

`deps` 任务用于手动更新 Charm 内部依赖（Fantasy 和 Catwalk）。设置 `GOPROXY=direct` 绕过 Go 模块代理的缓存延迟，确保能拉取到刚刚发布的版本。`GONOSUMDB=charm.land/*` 跳过 sumdb 校验（Charm 内部模块）。

### 12.3 依赖版本固定策略

项目不使用 `vendor/` 目录或 `go.sum` 之外的版本固定机制。GoReleaser 构建前运行 `go mod tidy` 确保 `go.sum` 与 `go.mod` 一致。CI 的 `build.yml` 也运行 `go mod tidy` 作为构建第一步。

### 12.4 提交消息约定

所有依赖更新 PR 使用 `chore(deps):` 前缀（Dependabot 配置）或手动遵循 conventional commits 规范。GoReleaser 变更日志将 `chore(deps)` 提交归入 "Deps" 分组，排序在 "New" 和 "Fixed" 之后。
